## Hallazgos priorizados y reproducción

### H1 · P1 — Consulta ambigua vacía cotizaciones, panel y ficha de cliente

1. Con sesión admin, abrir `/cotizaciones`: la tabla muestra **0**, aunque `public.cotizaciones` tiene **8** filas.
2. Abrir la ficha de `DEMO Vidriería Central`: muestra **Oportunidades (0)**, aunque el pipeline muestra varias ventas de ese cliente.
3. Abrir `/` y seleccionar **Todo**: muestra **0 oportunidades / $0** mientras `/ventas` muestra ocho oportunidades demo y la DB nueve oportunidades totales al inicio.

**Causa confirmada:** los `select` anidados de `app/cotizaciones/page.tsx:63,552`, `app/page.tsx:83` y `app/clientes/[id]/page.tsx:311` no nombran la relación. GET de solo lectura a PostgREST respondió **HTTP 300, `PGRST201`** en ambas direcciones, porque existen `cotizaciones_oportunidad_id_fkey` y `oportunidades_cotizacion_actual_id_fkey`. La UI convierte el error en lista vacía. **Impacto:** bloquea cotización, métricas comerciales y vista integral del cliente. Corregir las relaciones explícitas y repetir las tres rutas con datos demo antes del piloto.

### H2 · P1 — Cierres históricos aparentan entrega acreditada

1. Abrir `/ventas`: seis oportunidades demo figuran en **Venta Cerrada**.
2. Abrir `DEMO-OP-02` → **Producción y entregas**: muestra **Entrega Pendiente** y aviso de falta de acreditación.
3. DB: seis guías `entregada`, cero firmas y cero excepciones aprobadas; ninguna tiene `entrega_confirmada_at`. La migración nueva bloquea cierres futuros sin firma, como se comprobó en SQL, pero no reclasifica esos registros históricos.

**Impacto:** pipeline y operación dan señales contradictorias sobre entrega y cobranza. Revisar cada cierre demo/histórico y definir tratamiento antes de utilizar el estado como indicador operativo. No crear firmas ficticias para hacerlos pasar.

### H3 · P1 — Validación con equipo y catálogo real no disponible

`usuarios`: 1 admin, 1 `user`, 3 `mano_obra`; Lorena 0 y Katy 0, Edith 1. El catálogo tiene ocho `DEMO-HG-*` y cero referencias reales. Las pruebas de SQL por rol **no sustituyen** iniciar sesión con las personas y completar captación → cotización → operación → entrega → cobro. Se necesita la lista de productos, acceso de prueba de las vendedoras y un despliegue de la misma revisión del código. Mantener el piloto como no aprobado hasta entonces.

### H4 · P2 — Aviso de cobranza periódico sin programar

`public.generar_avisos_cobro()` existe, pero `pg_cron` no está instalado y `cron.job` no existe; el SQL propuesto sigue en `plans/pending-programar-avisos-cobro.sql`. Los avisos por cierre anterior existen, pero no hay evidencia de recordatorio diario/semanal automático. Definir activación y probar idempotencia antes de prometer seguimiento automático de vencidos.

### H5 · P2 — Línea base de migraciones y seguridad antes del despliegue

El listado remoto contiene los nombres de las migraciones nuevas, pero varias versiones difieren de los nombres de archivo locales (por ejemplo, `cierre_ocho_puntos` remoto `20260917133735` y archivo local `20260917132745`; `reportes_vistas_personales` remoto `20260927223150` y archivo local `20260927220603`). El plan histórico ya advierte que `0001_reconcile_schema.sql` no crea el entorno desde cero. Conciliar historial y ensayar restauración/despliegue antes de entregar acceso al equipo.
